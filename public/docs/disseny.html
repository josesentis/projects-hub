DESIGN.md — mAI Fitness

The app's design system. Tokens live in app/globals.css, components in app/ui.css. This file explains how to use them. Validated prototype (Today, Log, Coach): https://claude.ai/artifact/5hqDSRiA5wNbdkb9wLV52D

1. Atmosphere

Warm and calm like Her, clear and fast like Nike Training Club.

  • It feels like a mindfulness app: paper surfaces, a warm cream background, plenty of air, no borders, soft shadows.
  • It moves like NTC: big confident titles, full-bleed screens, one obvious action, a bottom tab bar, instant navigation.
  • The coach is a voice, not a form. What the coach says is set in a quiet italic serif; everything else is UI.
  • Nothing should look like a template: no grey borders around everything, no CAPS eyebrow labels, no identical chips, no emoji.

3. Type

  • Bricolage Grotesque (--font-bricolage, the default sans): everything. Numbers use .num (tabular figures, same face).

  • A small scale; hierarchy comes from weight and colour, not size:

    Class Phone Use
    ui-title 1.75rem / 720 (2.125rem on desktop) Screen title, once per screen
    ui-display 1.625rem / 760 The name of the thing a card is about (today's session)
    ui-h2 1.0625rem / 680 Sheet and card titles
    ui-h3 0.9375rem / 650 Section headings
    body / rows 0.9375rem List rows, inputs' companions
    ui-sub 0.875rem muted Secondary lines
    ui-label 0.75rem muted Field labels
    meta 0.8125rem Dates, counts under a title

  • Instrument Serif italic (ui-voice): only the coach's voice — its opening line, empty states where the coach speaks, the "how was it" line on the log. Never for UI chrome.

  • No uppercase labels.

  • This scale is the app's. The marketing landing (components/landing/*, landing-* classes) has its own and never uses ui-*.

4. Components (app/ui.css)

Rhythm. Three tokens drive spacing; use them instead of picking numbers: --gutter (1rem phone, 1.25rem desktop): screen edge, card padding, sheet content. --gap-section (1.25rem / 1.75rem): between blocks of a screen (ui-stack). --gap-item (0.625rem): between items of a block (ui-group).

Sizes. Buttons 40px (-lg 46px for the one main action of a screen, -sm 32px). Icon buttons 36px (ui-icon-btn-sm 30px, quiet, for move/remove inside cards). Pills 36px. Segmented 32px. Fields 42px with 16px text (iOS zoom); selects keep 1.9rem for the chevron and ellipsize. Radii: cards 18px, the hero card 22px, inner tiles 14–16px, fields 12px, sheets 24px.

Rules. A sheet's content owns its gutter (px-[var(--gutter)]); the sheet adds none, so padding never doubles. A radius is never larger than the padding beside it plus ~4px. Two buttons side by side beat two stacked. No borders on cards: surfaces separate by tone.

ui-title, ui-display, ui-h2, ui-h3, ui-sub, ui-label Type scale

5. Interaction quality — indispensable

Every interaction must feel native, finished and high end. Nothing may feel like a website in progress. This is a hard requirement of the project, at the same level as tests:

  • Check on a phone. Use a 390×844 viewport, with the keyboard open where there's input, before calling a screen done.
  • Chats (components/chat/*):
    • A conversation is a full-screen panel sized to the visual viewport (useVisualViewport). The header and message box keep their place, only the conversation scrolls, and the keyboard pushes the box up rather than covering it. The page behind never scrolls (useLockPageScroll).
    • It follows new content only while the reader is at the bottom (useStickToBottom). Otherwise a "latest" button appears.
    • ChatComposer rests as one line, opens into a textarea when focused, and grows with the text with an animated height. On touch, Return adds a line and the arrow sends; with a keyboard, Return sends. The send button never steals focus, so the keyboard stays open.
    • Typing is shown with TypingDots. A failed turn shows the error with "Try again". A reply the user has read is never removed from the screen.
  • Sheets rise from the bottom (fade on the scrim), sit above the keyboard and lock the page behind.
  • Motion:
    • Press states (active:scale) on everything tappable; entrances with ui-rise.
    • No layout jumps: skeletons keep the shape of what's loading.
    • Easing is cubic-bezier(0.2, 0.7, 0.2, 1), durations 150–380 ms, and every animation respects prefers-reduced-motion.

6. Layout & navigation

  • Phone first. Bottom tab bar: Today · Program · Progress · Coach · Profile. No top bar on phones; each screen has its own title (ui-title). Forms put back button, date and question in one row.
  • Desktop: a quiet canvas sidebar (active item = sand pill) with the account menu at its foot. No top bar: content starts at the top.
  • Today: date + big "Today" → week strip (coral = trained, dark = today, ring = planned) → the peach card "Up today" with one dark "Done it" button → progress line (sage ring) → "Doing something else today?" pills → floating coach bar.
  • Logging only records things done: the due session, a sport (duration + effort) or another workout. Never "a free day".

6.1 Desktop layout — one system for every screen

Desktop is a dashboard, not the phone column centred on a big screen. Layout expresses the content's hierarchy with patterns people already know; "two columns" is not a pattern.

Principles

  1. Every screen has one primary task. Decide it first, then the hierarchy; the layout follows from it.
  2. Equal importance, equal space. Two areas that matter the same (Today's training and food) get 6 | 6, never 8 | 4.
  3. Page-wide actions and inputs go in the PageHeader actions (top right, primary last) or in the full-width command bar under it (AppPage bar). Never in an aside corner.
  4. Section actions go in that section's header, on the right (SectionHeader action).
  5. An aside is only secondary context: metadata, history, a selected item's detail, "how I eat". If it is primary content it is a split, not an aside.
  6. Align to the grid. Rows of cards stretch to equal heights; an odd last card takes the whole row; tabular data uses real aligned columns (numbers right-aligned, tabular figures); no holes, no masonry gaps.
  7. One section header everywhere (SectionHeader: title, optional meta line, action right), so sections side by side start on the same line.
  8. Readable text: running text and forms stay under ~70ch / ~720px even on wide screens.

System (components/layout/; tokens and grid in app/ui.css › .ui-page*, .ui-section-*, .ui-tabs)

  • AppPage templates:
    • dashboard: main 8 + secondary context 4.
    • split: two primary areas, 6 | 6 (aside is the second area, rendered as a div).
    • wide: 12 (or 9 + 3 with an aside).
    • detail: master–detail, 7 | 5: a compact master (a calendar month) and a wide detail panel for the selected item. Below 1280 the detail stacks under the master, inline (no sheet).
    • focus: the first 8 columns, left-aligned so the title never moves.
  • AppPage bar: a full-width command bar under the header (page-wide input).
  • PageHeader: eyebrow · title · subtitle · actions · tabs. Eyebrow line reserved from tablet up, so titles share one baseline.
  • SectionHeader, AsideSection (secondary block with the same header), PageTabs (underline tabs from tablet up, never scrolling).
  • Breakpoints: phones (<768) one column, exactly as designed for mobile; tablet (768–1279) one wide column (max 45rem) next to an icon sidebar; desktop (≥1280) 12 columns, 24px gaps, max 1200px, left-aligned next to the sidebar.

7. Charts

Single-series data uses --color-chart (sage). Bars and rings have rounded ends, recessive gridlines, text in ink tokens. Validate any new palette with the dataviz validator.

8. Performance is part of the design

  • app/(dashboard)/loading.tsx shows a skeleton immediately; experimental.staleTimes keeps visited pages for instant back-and-forth.
  • Pages load in parallel and avoid repeated queries (React cache for the user and the active program). Use DB_LOG=1 to count queries.

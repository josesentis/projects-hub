This is NOT the Next.js you know

This version has breaking changes — APIs, conventions, and file structure may all differ from your training data. Read the relevant guide in node_modules/next/dist/docs/ before writing any code. Heed deprecation notices.

Tests are mandatory — no exceptions

Every new feature, lib function, API route or bug fix must include Vitest tests. Tests must pass before any deploy. The Netlify build command is npm test && npm run build — a failing test blocks deploy entirely.

Rules

  • Add tests in tests/lib/<module>.test.ts for every new file in lib/
  • Add proxy/auth tests in tests/proxy.test.ts for new protected routes
  • Run npm test locally before considering any task done
  • BCRYPT_ROUNDS=1 is set automatically in the test env (fast hashing)
  • Never mock the file system — the setup patches process.cwd() to a temp dir
  • Never call real Anthropic API or real web-push in tests — mock those modules with vi.mock
  • Test files live in tests/ mirroring the lib/ structure

Database tests (PGlite)

  • DB-layer and migration tests run against real Postgres in memory via tests/helpers/db.ts (createTestDb() applies the baseline, createMigratedDrizzle() also applies every migration).
  • Prefer this over mocking Drizzle query chains. tests/setup.ts closes every PGlite after each test and vitest.config.ts caps workers at 2 on Netlify/CI: each instance is a WASM heap and the build runs out of memory otherwise.

Migrations

  • They live in lib/db/migrations.ts (MIGRATIONS): each has a check (SQL boolean or function) and sql statements and/or a run(tx) for data. Only pending ones run, each in its own transaction. Write them idempotently anyway.
  • tests/lib/db/migrations.test.ts also fails if a table/column of lib/db/schema.ts has no migration, or a table lacks row-level security. Adding a column to schema.ts without a migration breaks the build (it only blows up in production otherwise).
  • Before applying to production: DATABASE_URL=<prod> npm run db:dry-run (runs everything in one transaction, prints row counts, rolls back). Apply with npm run db:apply -- --production or from /api/admin/run-migrations. Ask the user first.
  • JSON parameters in raw SQL must be cast $n::text::jsonb; a bare ::jsonb double-encodes with postgres-js and PGlite does not catch it.
  • npm run db:dev serves a local PGlite database on 127.0.0.1:5433 (DEV_DB_PORT to change it) with every migration applied. Never point local dev at production to try unreleased migrations.

Database connection

  • Production goes through Supabase's transaction pooler (:6543). The postgres client must not use prepared statements there (prepare: false, decided by usesPooler() in lib/db/index.ts, covered by tests/lib/db/client.test.ts). With prepared statements on, queries hang and writes are silently lost.
  • /api/health reports env presence, database round-trip times (first includes connecting) and pending migrations. Check it after every deploy.

Storage

  • Every upload uses a new path (uniqueStoragePath() in lib/storage/supabase.ts): the CDN keeps serving the old bytes for a reused path. uploadFile creates the bucket if it is missing.

Test framework

  • Vitest (npm test = vitest run)
  • Config: vitest.config.ts
  • Setup: tests/setup.ts (patches cwd, wipes data dir between tests)

End-to-end on a phone viewport

  • sh scripts/e2e/up.sh starts fake storage (:9999), a local PGlite database (:5439) and next dev on :3110 (never :3100: other projects use it). It seeds e2e@local (7 pieces, taste) and new@local (nothing yet, for onboarding). sh scripts/e2e/down.sh stops only what it started.
  • The scripts in scripts/e2e/ (chat, today, other, profile, onboarding, shots) drive headless Chrome at 390×844 with touch over the DevTools protocol and call the real Anthropic/Gemini APIs (cents per run). Open the screenshots they write: a passing script is not a visual check.

Operating rules (learned the hard way, in this project and in the sister one)

Production

  • Migrations first, code after. If the new code reads a table or column that does not exist yet, every screen breaks, and the admin banner to fix it cannot even load. Order: db:dry-run → the user applies the migration → only then push.
  • The user applies production migrations, not the agent. The auto-mode classifier blocks db:apply --production even with a clear instruction; do not try another route. Flow: the agent runs the dry-run and shows it; the user runs ! set -a; . ./.env.local; set +a; npm run db:apply -- --production; then the agent pushes and checks /api/version and /api/health.
  • Never point npm run dev or tests at the production database. Local is PGlite (scripts/e2e/up.sh, port 3110).
  • Production data is read only with explicit permission and only aggregates.
  • Nobody commits or pushes the same checkout while an agent is working in it. Background agents never share files, ports or databases, and never touch another session's services.
  • When "a change does not show up": 1) /api/version, 2) Netlify → Deploys (a failed build keeps the old version live), 3) the PWA cache. Only then the code.
  • The build is npm test && npm run build on Netlify, with the real keys in its environment: tests must not depend on where they run (tests/setup.ts clears them; the baseline SQL lives in tests/fixtures, because /drizzle is gitignored).

Code

  • Environment numbers go through lib/env.ts (blank, 0, negative or text → the default).
  • Every mutation that fails shows a notice; nothing leaves a list as if it had worked. Lists that change (wardrobe, calendar) are fetched again when mounted.
  • Every route that costs money checks lib/billing (gateTurn, photoAllowed); hiding a button is not protection. A turn the plan refuses answers 403 with a reason.
  • Side tasks on the cheap model (titles, matching what was worn) always have a plan B and their own usage_events feature.
  • A proposal replaces only the pending ones of its own family (proposalFamily).
  • Tests inject the Anthropic client (a fake with messages.stream/create), never vi.mock the whole SDK.
  • Admin audit logs record field names, never values.

Accessibility (a11y) — mandatory patterns

Escape key on every modal

Every modal or overlay must close on Escape. Use this exact pattern:

useEffect(() => {
  if (!open) return                         // only attach when modal is visible
  const onKey = (e: KeyboardEvent) => { if (e.key === 'Escape') onClose() }
  document.addEventListener('keydown', onKey)
  return () => document.removeEventListener('keydown', onKey)
}, [open, onClose])
  • For always-mounted modals (no open toggle), omit the guard: attach on mount, clean up on unmount.
  • onClose must be stable (passed as prop or wrapped in useCallback) to avoid stale closures.

Images

All <img> elements must have user-select: none — enforced globally via app/globals.css.
Never add draggable={true} to images.

Focus rings

All interactive elements (buttons, links, inputs, selects) must have a visible focus ring. Use:

  • focus:outline-none focus:ring-2 focus:ring-black/30 on light backgrounds
  • focus:outline-none focus:ring-2 focus:ring-white/40 on dark backgrounds (e.g. sidebar)

Never use bare focus:outline-none without a replacement ring.

Dropdown / popover pattern

Every dropdown must close on both outside click AND Escape. Use two useEffect calls:

// Outside click
useEffect(() => {
  function handleClick(e: MouseEvent) {
    if (ref.current && !ref.current.contains(e.target as Node)) setOpen(false)
  }
  document.addEventListener('mousedown', handleClick)
  return () => document.removeEventListener('mousedown', handleClick)
}, [])

// Escape key (only attach when open)
useEffect(() => {
  if (!open) return
  const onKey = (e: KeyboardEvent) => { if (e.key === 'Escape') setOpen(false) }
  document.addEventListener('keydown', onKey)
  return () => document.removeEventListener('keydown', onKey)
}, [open])

The trigger button must have aria-expanded={open} and aria-haspopup="true".

Dialogs / modals

Every modal overlay must have role="dialog" and aria-modal="true" on the outermost div, plus an aria-label describing its purpose:

<div role="dialog" aria-modal="true" aria-label="Modal title" className="fixed inset-0 …">

Non-blocking banners (e.g. cookie consent) use aria-modal="false".

Toolbars

Groups of action buttons that operate on a selection (e.g. bulk action bars) must have role="toolbar" and aria-label:

<div role="toolbar" aria-label="Bulk actions" …>

CSS gotchas

Images in cropping/canvas contexts

Tailwind's preflight and browser CSS reset apply max-width: 100% to all <img> elements.
When positioning images absolutely with an explicit pixel width, always add maxWidth: 'none' and maxHeight: 'none' to the inline style, or the image will be clamped to the container width and lose its aspect ratio.

<img style={{ width: dispW, height: dispH, maxWidth: 'none', maxHeight: 'none' }} />

Admin Analytics

  • /admin/analytics: AI cost per month for the last 12 months (stacked by feature, forecast for the month in progress, the configured monthly budgets as a reference line) and a per-month detail (/api/admin/analytics?month=YYYY-MM).
  • Derived from usage_events (aggregated in SQL by getMonthlyCostRowsDb), shaped by the pure lib/analytics/cost-history.ts. Months are Europe/Madrid calendar months. The same module and chart (components/admin/CostHistoryChart.tsx, colours via .cost-chart vars in app/globals.css) live in mAI Fitness; keep them in sync.
  • Record every paid AI call with addUsageEventDb and a feature name, or it won't show up.

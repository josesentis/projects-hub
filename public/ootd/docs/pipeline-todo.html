Image pipeline — garment extraction + AI collage

Superseded (2026-10): outfits are now generated as photos of a person — see ai/OUTFIT_IMAGE_PIPELINE.md. Section "B. AI collage" is obsolete. Section A (garment extraction) is the base for ai/WARDROBE_RECONSTRUCTION_NEXT.md.

Goal: a photo (even a selfie) → detect each garment → reconstruct each one as a clean, unified product image → save as its own wardrobe item → build the collage with AI, not canvas.

Engine: Claude understands (detects garments); Gemini 2.5 Flash Image ("nano-banana") makes the pixels (reconstruction + collage).

✅ Done (this pass — engine + tests, nothing wired into the live flow yet)

  • lib/gemini.ts — nano-banana client (REST, no SDK dep):
    • reconstructGarment(source, garment) → isolated product shot of ONE garment
    • composeCollage(images, { style }) → one editorial flat-lay collage
    • isGeminiConfigured(), generateImage(), fixed STUDIO_RECIPE, prompt builders
  • lib/ai.ts — detectGarments(image) + parseDetectedGarments(): Claude returns a JSON list of every garment in the photo (name / category / description), ignoring face, skin, hands and background. This is the piece that fixes the "selfie glued whole into the collage" problem.
  • lib/usage-cost.ts — geminiImageCostUsd(n) (~$0.039 / image).
  • .env.local.example — GEMINI_API_KEY, GEMINI_IMAGE_MODEL.
  • Tests: tests/lib/gemini.test.ts, extended tests/lib/ai.test.ts (25 new/related, all green).

Nothing above changes current behaviour — it's inert until wired + a key is set.

A. Garment extraction on upload → replaces "removebg of the whole photo"

Decided rules:

  • Max 2 garments per photo (cap detection output at 2 — the 2 most prominent).
  • Discard the original photo — keep only the reconstructed per-garment images.
  • Few photos → analyse immediately; many photos → background (survives the browser closing → some items land analysed, the rest finish server-side).

Core op POST /api/wardrobe/extract (pattern: copy app/api/wardrobe/route.ts

  • the Claude-key plumbing from app/api/analyze/wardrobe/[id]/route.ts):
  1. Receive the photo → shrinkForApi → base64.
  2. detectGarments(base64, mime, { apiKey: ANTHROPIC_API_KEY, model }) → take ≤2.
  3. For each garment → reconstructGarment(...) → uploadFile('wardrobe/{id}.png') → addWardrobeItemDb({ ...garment, analyzed: true, bgRemoved: true }).
  4. Delete the original upload from storage.
  5. Track usage: geminiImageCostUsd(n) + Claude tokens.

Immediate vs background (this is new — current analysis is client-driven and dies when the tab closes):

  • Threshold in handleFiles (wardrobe/page.tsx): ≤ 3 photos → call /extract synchronously (user waits behind AnalyzingOverlay, sees items appear).
  • > 3 photos → enqueue and return instantly. Needs a server-side queue:
    • New table extraction_jobs (userId, storagePath, status pending|done|error).
    • Upload stashes the raw photos + a pending row; UI shows the pending items as skeletons that fill in as they get processed.
    • A drain endpoint POST /api/cron/extract (protected by CRON_SECRET) processes a batch of pending jobs. Trigger it two ways: a best-effort kick right after enqueue (serverless, handles small backlogs) and a frequent Netlify Scheduled Function (~1 min) so it keeps draining after the tab closes. NOTE: the existing app/api/cron/daily is daily → too slow; add the ~1-min one.

💰 Cost (nano-banana ≈ $0.039 / generated image)

  • Add a garment photo (selfie, 2 items): detection (Claude) ~$0.01–0.02
    • 2 × $0.039 reconstruction ≈ ~$0.10 per upload.
  • Build a 30-item wardrobe: ≈ ~$1.2 one-off.
  • Each AI collage: ~$0.04. Reconstruction runs once per garment (cached), never per outfit — that's what keeps it cheap.

⚠️ Watch out for

  • Fidelity: reconstruction must keep the real garment (exact colour, print, logo). The prompt says "preserve"; validate on real photos and tune if a detail drifts. If it invents details, we switch to lower-denoise img2img.
  • Latency: N image calls per upload → keep the async overlay; consider a small concurrency limit (like the existing ANALYZE_CONCURRENCY = 3).
  • Never break prod: everything gates on isGeminiConfigured() — no key ⇒ current canvas/removebg flow stays.

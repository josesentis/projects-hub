@ai/DESIGN.md

This is NOT the Next.js you know

This version has breaking changes — APIs, conventions, and file structure may all differ from your training data. Read the relevant guide in node_modules/next/dist/docs/ before writing any code. Heed deprecation notices.

Interactions must be high end — no exceptions

Every screen must behave like a polished native app; nothing may feel WIP. Follow ai/DESIGN.md §5 (chats, sheets, keyboard, motion) and check new UI on a 390×844 viewport with the keyboard open before calling it done.

  • The page scrolls again after every sheet. Lock the page only with useLockPageScroll (components/chat/useVisualViewport.ts), never by setting overflow yourself: locks are counted (lib/ui/scroll-lock.ts), so two sheets open at once (the terms sheet under a meal's sheet) can close in any order. tests/lib/ui/scroll-lock.test.ts guards it.
  • Fields never zoom the phone. iOS zooms into any field under 16px on focus. app/globals.css forces 16px on every input, textarea and select on touch or narrow screens (!important in @layer base, which beats any !text-* utility). Style fields freely on desktop; don't fight it on phones, and never block zoom in the viewport (maximum-scale). tests/lib/ui/no-zoom-fields.test.ts guards it.
  • zod stays on the server. A client component that imports, even through lib, a module importing zod ships the whole library to the phone (~95 KB gzipped). Constants and pure helpers screens need live in modules without it (lib/nutrition/nutrients.ts, lib/nutrition/extras.ts, lib/training/disciplines.ts, lib/admin/trial-dates.ts); schemas go next to them (extras-schema.ts, recipe.ts, template.ts). tests/lib/ui/no-zod-in-client.test.ts guards it.
  • Fonts: only Bricolage Grotesque (text) and Instrument Serif (the coach's voice), from app/layout.tsx. Each font is downloaded before text shows; add one only when a screen uses it.

Tests are mandatory — no exceptions

Every new feature, lib function, API route or bug fix must include Vitest tests. Tests must pass before any deploy. The Netlify build command is npm test && npm run migrate:deploy && npm run build, so a failing test blocks the deploy entirely. GitHub CI runs the same tests on every push.

Rules

  • Add tests in tests/lib/<module>.test.ts for every new file in lib/
  • Add proxy/auth tests in tests/proxy.test.ts for new protected routes
  • Run npm test locally before considering any task done
  • BCRYPT_ROUNDS=1 is set automatically in the test env (fast hashing)
  • Never mock the file system — the setup patches process.cwd() to a temp dir
  • Never call real Anthropic API or real web-push in tests — mock those modules with vi.mock
  • Test files live in tests/ mirroring the lib/ structure

Database tests (PGlite)

  • DB-layer and migration tests run against real Postgres in memory via tests/helpers/db.ts (createTestDb() applies the drizzle baseline).
  • Prefer this over mocking Drizzle query chains.

Migrations

  • Incremental migrations live in lib/db/migrations.ts (MIGRATIONS). Each one has a check SQL expression and sql statements and/or a run(tx) function for data migrations.
  • Only pending migrations run, each inside a transaction. Write them idempotently anyway.
  • Expand/contract: a migration only adds (columns, tables, indexes, backfills) and the code that ships with it must also work before it runs. Anything that removes or renames what running code uses gets destructive: true and ships in a later release.
  • Applied on deploy: the Netlify build is npm test && npm run migrate:deploy && npm run build. scripts/migrate-on-deploy.mts (logic in lib/db/migrate-deploy.ts) runs only when CONTEXT=production: it dry-runs every pending migration in one rolled-back transaction, then applies them, if none is destructive. A pending destructive migration, a dry-run failure or a missing DATABASE_URL fails the build. It refuses a local DATABASE_URL (MIGRATE_DEPLOY_ALLOW_LOCAL=1 only for local simulations). With nothing pending it does nothing.
  • By hand (destructive migrations, or to check first): DATABASE_URL=<prod> npm run db:dry-run, which runs all pending migrations in one transaction, prints row counts and unmatched exercise names, and rolls back; then npm run db:apply -- --production or the admin banner (/api/admin/run-migrations).
  • A pending migration must not take the app down: lib/db/users.ts › selectUsers retries without the users columns the table doesn't have yet (Postgres 42703), so the layout and the admin banner keep loading. The layout also tolerates a failing plan lookup.
  • JSON parameters in raw SQL must be cast $n::text::jsonb. A bare ::jsonb makes postgres-js double-encode the value, and PGlite does not catch this.
  • Every new migration needs a test in tests/lib/db/migrations.test.ts (or its own file). tests/lib/db/migrate-deploy.test.ts checks that any migration with DROP TABLE / DROP COLUMN / TRUNCATE is flagged destructive.

CI and deploys

  • .github/workflows/ci.yml runs on every push and PR to main: npm ci, the tests with a Netlify-like env (NETLIFY=true, COACH_MONTHLY_TOKEN_LIMIT=0, empty optional vars), and tsc. Lint runs there too but doesn't block yet: older auth and banner screens still have errors to clear.
  • When "a change doesn't show": check https://maifitness.netlify.app/api/version (the deployed commit) and Netlify → Deploys. A failing test or migration blocks the deploy, and production keeps the previous build.
  • Parse env vars defensively. An empty or 0 value must fall back to the default: an empty COACH_MONTHLY_TOKEN_LIMIT once failed tests only on Netlify and blocked every deploy for days.
  • Don't commit or push while agents are working in the checkout: a commit snapshots their unfinished work.

Database connection

  • Production goes through Supabase's transaction pooler (:6543). The postgres client must not use prepared statements there (prepare: false, decided by usesPooler() in lib/db/index.ts). With prepared statements on, queries hang and writes are silently lost; that is how coach replies stopped being saved.

Local development database

  • npm run db:dev starts PGlite on 127.0.0.1:5433, with data in .pglite/, all migrations applied, and a seeded admin dev@local / devdevdev.
  • Run the app against it with DATABASE_URL=postgresql://postgres@127.0.0.1:5433/postgres npm run dev.
  • npm run db:seed adds a legacy-shaped routine (4 sessions), about 6 weeks of workout logs and weight logs for the dev user.
  • Scripts in scripts/ run with tsx, so the @/ path alias works.
  • Never point local dev at the production database to try out unreleased migrations.

Meal planning (lib/nutrition, lib/coach/nutrition-*)

  • It's a meal plan, not a food tracker. The deliverable is concrete grams per ingredient for the user's body, training and goal.
  • The plan is never an obligation (training is the one that gets done): food copy never says missed/failed, uses no red states, the coach nudges and never scolds; swapping a meal is first-class.
  • The app does the maths, never the model:
    • targets.ts computes resting energy (Mifflin-St Jeor) × lifestyle + the user's real training energy, then the goal's deficit or surplus with safety limits (≤1 % of body weight a week, ≤25 % deficit, ≥ resting energy). Protein is set per kg of a BMI-25 reference weight.
    • recipe.ts › fitRecipe scales a recipe's protein and carbohydrate groups (then fat) so one serving hits a meal's kcal and protein, rounded to weighable or countable amounts. Eggs stop at 4 and burgers at 2 per meal (CAP_GRAMS); egg whites or carbohydrate take the rest.
    • Recipes are stored as one generic serving with food ids from foods.ts (per 100 g as bought).
  • Recipes come from people, not the model:
    • The base book (recipe-book.ts, ~85 real home-cooking dishes reviewed by a user, ca/es/en) is stored as shared rows (recipes.user_id NULL, source='book', migration 0025_recipe_book); name and steps are localised from the module (localizeRecipe). Edit the module and re-run the seed (it upserts).
    • Per user: favourites and "don't suggest it again" for book recipes live in recipe_prefs (their own recipes keep favorite / archived on the row), via setRecipePref; swaps_away counts how often a dish is swapped away.
    • The coach plans ONLY with the visible book + the user's recipes (propose_meal_plan / propose_meal_changes reject unknown, hidden or too-varied plans: ≤4 lunches/dinners, ≤2 breakfasts/snacks — plan-edit.ts › rotationIssues). New dishes only via save_recipe (theirs, or a suggestion they asked for). "My way" = propose_recipe_change (before → after card; accepting saves their version with base_recipe_id, hides the original, replaces it in the plan).
  • A strong lunch, a light dinner (plan.ts › DINNER_SHIFT, heavyAtDinner; book reviewed by a user 2026-10-19, migration 0040_book_meals): heavy dishes (pasta, rice dishes, legumes, stews; book tag heavy, recipe-book.ts › HEAVY) are lunch only; bowls, potato, bread and grilled meat go to both. mealTargets(day) moves part of the day's energy from dinner to lunch by day.goal (cut 6 %, maintain/recomp 4 %, gain 0) while protein stays, so the same dish at dinner comes with less potato or bread. Gaining, heavy dishes may go to dinner too (findMealAlternatives(…, { heavyDinner })). The week's menu replaces a heavy dinner of the base plan first (beyond the quota) and the AI is told; propose_meal_plan / propose_meal_changes refuse a book dish at a meal it isn't for (checkMeals). Their own recipes go where they say; save_recipe asks for lunch only + heavy on heavy dishes.
  • How the user eats ("Com menjo"): food_memory facts (habit, like, dislike, cooking, note) written by the coach (remember_food_preference) or the user (Food → Receptes card), plus hidden dishes and often-swapped ones (taste.ts). All in the coach snapshot. scripts/import-food-votes.mts imports a book review for a user (personal data: only with their permission).
  • Like programs:
    • a versioned base plan (meal_plans, meal_plan_versions; never edit a template, add a version). Food → Pla shows the week grid with grams, the rotation and the versions, and edits by hand (plan-edit.ts › applyPlanEdits, POST /api/meals/plan, each edit = a new manual version with a readable summary);
    • each real week is materialised as planned_meals by syncWeekMeals: base plan + that week's adaptations (meal_weeks), never touching history.
  • Each week has its own menu, written by AI; the rules are the net (week-menu.ts, lib/services/week-menu.ts, lib/coach/week-menu.ts, meal_weeks.menu, migration 0037_week_menu): the base plan stays as the person left it, but nobody eats the same seven days every week, and the menu must learn from how they eat.
    • Laid out at once by rules (planWeekMenu, claimWeekMenu) the first time a week is opened or from Monday's cron: part of the dishes eaten the week before give way to others for the same meal, fitted to the same target, from their recipes and the visible book (up to half of the different lunches and dinners, one breakfast or snack at most, favourites last, never a dish from the last two weeks' menus; same week → same menu).
    • Then the AI writes it (requestWeekMenu → netlify/functions/week-review-background.mts with { menuWeek }, detached in local dev; runWeekMenuAI): one call per person and week on the small model (WEEK_MENU_MODEL, default the cheap one; recorded as feature week_menu). gatherMenuDossier gives it the goal, the base plan with ids, the last four weeks as they went (what was on the menu, replaced by something else, skipped), what the person said about how they eat (food_memory), favourites and dishes swapped away, the dishes that can come in per meal (already checked to fit), and the rules' menu as a hint. It answers with set_week_menu: a note to the person and the swaps. sanitizeMenu keeps it inside what the app can serve (only the plan's dishes, only offered ids, no dish twice); the app fits the grams. No key, no budget, no answer: the rules' menu stays (aiFailed), and it is asked once (aiPendingSince).
    • Never the same thing twice in a day (sameDayClashes, withoutClashes): lunch and dinner of a day never end up being the same dish or sharing their main protein because of the menu. The rules skip such replacements and rotate out first the dishes that already clash in the base plan; the AI is told the rule, is shown the plan's clashes to fix, is only offered dishes that can go in without one, and sanitizeMenu drops what breaks it. Stored menus carry checked (MENU_CHECK): an older one is held to the rule the next time the week opens, and written again by the AI when it broke it.
    • syncWeekMeals applies the menu under the week's adaptations (applyMenu), so "back to the plan" on a meal returns to the week's dish. A first week, or weeks that don't adapt (adaptFood off), keep the plan (source: 'plan').
    • What the person sets stays: a meal changed "from now on" (swapMeal scope base) is stored with keep: true in the template: neither the rules nor the AI replace that day's meal, this week or later, even when the dish is the one the plan already had there.
    • Getting the week ready (lib/nutrition/week-ready.ts, getWeekReady / decideWeek / presentWeekAhead in lib/services/week-menu.ts): many people prepare the week on Sunday. On Sunday from 10:00 (local) the hourly cron lays out the coming week's menu and sends one push (week_ahead, topic food, once per week) to /food/week; Today and Food show WeekReadyCard on Sunday (the coming week) and all Monday (the one starting) until the week is accepted or the card closed (menu.decision, stored in meal_weeks.menu; POST /api/meals/week-menu { monday, decision }). /food/week (WeekPrepClient) shows the week day by day with the AI's note and the days that train: accept it as it is, change any dish, or — optional, for unusual weeks — "How will your week be?" opens the coach with it (the snapshot's "Getting the week ready" section; adapt_week may change that week on Sunday). Not accepted, it counts as proposed. Accepted, the AI's menu never rewrites it, and Shopping shows the whole accepted week (ShoppingView.ahead). A week laid out takes the week before's "already have it" (claimWeekMenu(…, have); setHave(…, monday)). Monday's cron still sends "new week" (week_ready). The app never tracks what is cooked ahead (no tuppers, no batch-cooking tips).
    • The same dish on other days (repeatsOf, MealView.repeats): changing a dish that is planned later that week at the same meal asks "only Monday, or Wednesday too?" (MealSwapSheet); swapMeal(…, { also }) changes those meals the same way, this week or from now on (one plan version for all those weekdays). A lunch and a dinner that are the same dish are different meals. Never the same dish twice a day: days that already have the new dish at another meal are not offered (freeRepeats, repeats[].taken) and swapMeal leaves them as they are.
  • A dish from this week first (lib/nutrition/trade.ts, getMealAlternatives().trades, POST /api/meals/:id/swap { withMealId }): "Change" opens with this week's other meals to trade with (nearest first). The two dishes swap places, this week only (two swap adaptations), each fitted to its new meal; not a "not for me" (swaps_away untouched). Lunch and dinner trade with each other (a heavy dish goes to dinner only when gaining); breakfast and snacks only with their own; only planned meals from today on; never the same dish twice in a day. The suggestions below leave out every dish already on this week.
  • Alternatives (alternatives.ts, no AI): ranked dishes for a meal by reason (no time, not in the mood, missing something), fitted to that meal's target. A list to choose from, not ten salmons (varied): at most two with the original's main protein and two of any other; the dishes the person usually has at that meal (the plan's and this week's, usual) rank up. POST /api/meals/:id/swap: only this time (a week adaptation) or from now on (a new base version); "back to the plan" resets it.
  • Meal photos (lib/coach/food-photo.ts, lib/services/food-photo.ts, POST/GET /api/food-extras/photo, components/food/PhotoReader.tsx): "Take a photo" in "Add food" and in a meal's "I ate something else". Phones and tablets only (lib/device/mobile.ts): the browser asks the device (user agent, userAgentData.mobile, an iPad calling itself a Mac told apart by touch), never the width; on a computer the option isn't shown at all, and the route answers 403 mobile_only to what is surely a computer. The phone shrinks it to 1280 px JPEG (lib/photo/shrink.ts, metadata dropped), an optional note goes with it ("I ate half"), and one call to FOOD_PHOTO_MODEL (default the goals model, Sonnet; it doesn't take a forced tool, so the answer is read leniently) names foods from the table with grams as bought, or estimates. The result is the same reviewed list as words; nothing is saved until the person confirms. The photo is never stored. Each read is a food_photo usage event (≈1 cent; Admin → Analytics "Meal photos") and the month's count is the allowance (Madrid months; a photo with no food still counts, a refusal before the call doesn't). Used up: 429 photo_limit, the UI says words still work and offers "More photos" (foodPhotos lock). Gate: food on (foodGate 'food') and health consent.
  • Today answers, Food plans: Today's meal rows are a one-tap eaten toggle (tap again = planned; sendOrQueue, idempotent) plus "Change"; Food and the recipe page never mark meals. Logging stays optional: an unmarked meal counts as eaten as planned. 'Something else' is estimated. Eaten with changes (components/food/MealEditSheet.tsx, the pencil on an eaten meal or "I had it with changes" in the swap sheet): the same dish as it really was that day — amounts changed, items out, anything added from the food table or said in words (/api/food-extras/parse). POST /api/meals/:id { status: 'eaten', edited } stores the resolved items in planned_meals.other.edited (status stays eaten, gate check, not Precise); day.ts counts them plus the meal's supplements instead of the fitted recipe, the row says "with changes", "As planned" or tapping the circle forgets them. day.ts rebalances the rest of the day and carries what can't fit to the rest of the week (±10 % a day, protein never cut).
  • Coach:
    • Facts are saved at once: update_nutrition_profile, save_recipe, adapt_week, log_meal, remember_food_preference, hide_recipe.
    • Targets, plan changes and recipe versions are proposals the user accepts or rejects: propose_nutrition_targets, propose_meal_plan, propose_meal_changes, propose_recipe_change.
    • Before the first plan it asks what they ate this week and what they cook often.
    • A new proposal only supersedes pending ones of the same family.
  • A productive chat (lib/coach/prompt.ts › "Be quick"): the snapshot opens with "Today at a glance" (context.ts › formatGlance: days since the last workout, the week, what today holds, one-off sessions already planned) so the coach never asks for it; it sizes the request (one day vs. the program), asks at most once and acts in the same turn. offer_replies shows tappable answers under a question (ChatItem kind replies, components/chat/QuickReplies.tsx, shown only while they are the last thing said); a turn that only offers replies ends without another model round (run.ts).
  • Local data: npm run db:seed:food seeds a plan from the book for dev@local.

One goal for training and food

  • users.goal_focus (lib/training/goal.ts: fat_loss | muscle | recomp | performance | maintain), set in Profile or by the coach (update_training_profile.goalFocus). Changing it re-points the diet direction (alignDietWithFocus, lib/services/goal.ts); accepted targets are never changed silently.
  • coherence() lists where program, block and targets pull apart (e.g. a ≥15 % deficit in a strength block); the coach snapshot shows it under "Goal".
  • Calories follow training (lib/nutrition/cycling.ts): each day of the week gets more or less energy by its exercise kcal (the program's sessions on their current date, done or still to do; a workout that stood in for a session is the program's), max ±15 %, same weekly total, protein fixed.
  • Training outside the program feeds the next days, by the goal (splitWorkouts, extraEnergyBack): the day itself stays as planned; its kcal come back on the next two days, half each, by the diet goal (EXTRA_BACK: gain and maintain all, recomp half, cut none), unless the week's deficit goes past 25 % of maintenance, then what goes past comes back; at most 15 % of a day's target. Saturday's and Sunday's feed Monday and Tuesday. DayView.extraBack, said under the day (DayKind). A day checked in as rest or "something else" is a rest day for food at once: its session moves to a free day, and when there is none left (Sunday) the open session counts nothing (trainingByDate › off). DayView.trainingKcal / shift.
  • Accepted targets store basis (training kcal/day, program, block). lib/nutrition/signals.ts raises targets_stale (new program, new block, ≥15 % and ≥75 kcal drift), deficit_strength, weight_flat, low_protein, rpe_deficit; they join the training signals in gatherCoachData and the daily proactive pick.
  • Progress → Goal (/api/metrics/goal, getGoalProgress): 8 weeks of weight, key-lift e1RM, days close to the meal plan (informational, neutral) and sessions done, plus goalVerdict(). Past meal weeks are read as stored, never materialised from today's plan.

Usage profiles (lib/profile/usage.ts)

  • Not roles: four areas with a level each — training (simple / normal / detailed), food (off / guide / plan / precise), body (off / light / full), coach (quiet / normal / close) — and presets: training_only, balanced, demanding. Stored in users.usage (null until chosen: Today asks once; Profile edits it).
  • Ask capabilities(usage) instead of checking levels in screens: it gates the Food tab (hiddenHrefs), Today's meals and weigh-in card (weighInDue), Progress tabs (progressTabs), numbers vs household portions (amountStyleFor → lib/nutrition/household.ts), exact grams (fitRecipe(..., { exact })), the simple log, the rest timer, coach food tools (refused when food is off), signals (areaAllows) and proactive threads (allowsSignal). Client components read it with useUsage().
  • Hiding a part never deletes its data.

Goal phases (lib/training/phases.ts, lib/db/phases.ts)

  • The goal is a series of phases (focus, dates, weight mode target / band / none, band as % of body weight a week). They never overlap: createPhase trims the current one and replaces later ones. programs.goal_phase_id links a program to its phase. users.goal_focus is only a mirror of today's phase (syncFocusMirror).
  • The coach proposes phases with propose_goal_phase (now or scheduled); a phase_start thread opens a few days before one starts.

Adaptive food (lib/nutrition/adaptive.ts, lib/services/adaptive.ts)

  • Weekly, from the daily cron: weight trend (≥3 weigh-ins in 10 days), learned maintenance, the phase's band, strength first when weight is not the goal. Moderate changes apply alone (≤150 kcal/day per week, from tomorrow, energy_adjustments, undo); bigger ones open a food_adjust thread and the coach proposes propose_nutrition_targets with adjustKcal. Protein never changes. Day targets add adjustmentFor(...); accepted targets don't include it.
  • Targets store the weight they assumed (basis.weightKg); a 3 % drift raises targets_stale.

Billing and the beta (lib/billing, lib/analytics, ai/BETA.md)

  • Plans (lib/billing/plans.ts): free, Entrena 4,99/39,99 €, Coach 9,99/79,99 €, Coach+ 16,99/149,99 € (VAT included). Each matches a usage preset and caps usage levels: Precise food and the "close" coach are Coach+ only; Entrena and free have food off. Meal photos a month (foodPhotosPerMonth): free and Entrena 0, Coach 10, Coach+ 80 (trial and full access: Coach+'s; admins and own keys: no cap; payments off: FOOD_PHOTO_BETA_LIMIT, Coach+'s 80).
  • Entitlements (lib/billing/entitlements.ts › entitlementsFor(user, subscription, now)): the 14-day trial (users.trial_ends_at, everything open, no card), the paid plan (Stripe status active / trialing / past_due, or cancelled until its period ends), free, or admin. Gives the monthly coach budget (messages and tokens; admins and BYOK have none) and ads (free only, ADS_ENABLED). Screens use getEntitlements / getBillingView (lib/services/billing.ts).
  • Full access (users.comp_access, migration 0032_comp_access): an admin grants it from Admin → Users for friends and collaborators. It beats the trial, free and paid plans: Coach+ levels, no ads, no message cap, only a monthly token guard (COMP_MONTHLY_TOKEN_LIMIT, 20M by default), with or without Stripe. The coach honours it in monthlyTokenLimit too.
  • Last sign-in (users.last_sign_in_at, migration 0038_last_sign_in, shown in Admin → Users): stamped by recordSignInDb in the routes where the person signs in themself (password, Google, Apple, the email-verification link). /api/admin/impersonate never calls it, and silent session renewals don't either; "Last active" (product events) is the other one. The Users table shows "Last seen", the latest of the two (lib/admin/last-seen.ts): sessions last up to 30 days, so the sign-in alone stays blank for daily users. Events sent while an admin views the account as someone (/api/events with impersonatedBy) are not recorded. A new sign-in route must call it.
  • Admin → Users edit (components/admin/UserEditSheet.tsx, PATCH /api/admin/users/:id { edit }): validated by lib/admin/user-edit.ts; uniqueness and "no demoting yourself" in lib/services/admin-users.ts. Each edit is logged as an admin_user_edit event on the admin with the changed field names, never their values.
  • Stripe is the source of truth. POST /api/billing/checkout (Checkout, Stripe Tax, founder coupon or promo codes, keeps the remaining trial), /api/billing/portal, and POST /api/billing/webhook, which is public, signature-verified and handles each event once via stripe_events. Without STRIPE_SECRET_KEY the UI says "coming soon". Products and prices: npm run stripe:setup (test key). Tests mock Stripe, never call it.
  • Product events (product_events, lib/db/beta.ts › track()): signup, trial, app open, activated, session logged, coach message, meal checked or swapped, recipe changed, phase set, paywall, limit, checkout, subscription. They never store what people wrote and never fail a request. The browser may only send the few in CLIENT_EVENTS (POST /api/events).
  • Beta: invite codes per cohort (/register?invite=CODE sets the cohort, the founder price and a usage preset), Profile → feedback (text + NPS), a Tally survey card on Today in weeks 2/4/6 (BETA_SURVEY_URL), and Admin → Beta with activation, D1/D7/D30, coach use, AI cost and NPS per cohort.
  • Where people come from (lib/analytics/source.ts): any link with ?ref=<channel> (or utm_source) leaves a first-touch cookie (mai_src, 30 days, set in proxy.ts); the sign-up (email form, and Google/Apple through the signed OAuth state) records it as signup.props.source. Payment guarantee (lib/billing/entitlements.ts, lib/services/billing.ts)

The week is a to-do list

  • Planned sessions have a suggested day. In the current week the user can do them in any order on any day: lib/training/week.ts (weekBoard, moveToToday, postponeToday). Open sessions are not "missed" until the week is over (adherence, inactivity signal).
  • reconcilePlanned matches current-week sessions by week + session (so moved ones stay put) and later weeks by exact date (so template day changes apply).
  • Daily check-in (daily_checkins, lib/training/checkin.ts): as_planned | sore (+ body areas) | other | rest. Quick answers are resolved without AI; free text and week reorganisation go to the coach (propose_schedule, proposal kind schedule).
  • One page per session (components/log/LogForm.tsx): Today's card has one action, "Open the session", and that page is where the session is read (target, last time, the program's note per exercise, the week's note), changed and logged. Order and "not today" are one tap on each exercise (↑ ↓ ✕; the moved card glows, keeps focus on its arrow and is announced; ✕ shows an undo bar for 6 s that brings back what was typed). "Change" opens ExerciseOptions: alternatives with what to aim for (GET /api/exercises/:id/alternatives?planned=&item=, alternativeTargets), any other exercise, back to the programmed one.
  • A replacement is always for the same muscle group (lib/training/muscle-groups.ts: lats/traps → back, glutes + hamstrings → posterior…). findAlternatives keeps a candidate only when its main muscle is in the original's group, or for the very same movement pattern when it also works that group (bench → close-grip bench, deadlift → RDL), ranked after the same group; conditioning, jumps, Olympic lifts, cardio and mobility keep their kind. "Search another" opens the picker on that group (GET /api/exercises?like=<id> → group) with "All" to widen it. A test checks every catalog exercise. Changes live in the form, never in the program. Whatever was touched is kept on the phone until the workout is saved (lib/log/draft-store.ts, one draft per session in localStorage, two weeks): closing the page loses nothing, the page says "picking up where you left off" with "Start over", and Today's button reads "Continue the session".
  • Activities outside the program (walk, boxing…) are logged with POST /api/workouts/quick (lib/training/activities.ts MET per activity) and count as extras.
  • Something else instead of a session counts by itself (lib/training/coverage.ts, no AI): the person only trains; the app decides. Each template session may carry standIn (any | any_cardio | same_discipline | activities | strength | mind_body | none, optional minMins), written by the coach from the goal (propose_program, add_session / update_session; prompt › "Sessions done some other way"). Without one, ruleFor derives it from today's phase: strength → strength on half its muscles; yoga/mobility → mind_body; run/swim/cycling → any_cardio, same_discipline with a performance focus or that sport; "something active" (hiit/other) → any, any_cardio with performance or a sport. The phase's sport (goal_phases.sport, migration 0039_phase_sport, propose_goal_phase.sport) is the specific aim ("get better at basketball"). Dose, like a watch: a workout is a session at ≥ 30 min (or 60 % of the session, or minMins) and moderate intensity (activity MET ≥ 3, ×0.85 when logged easy); weights logged by exercise always are; yoga/mobility only need their length. Shorter or gentler activity is minutes and energy. One to one (assignCoverage, strictest rule first): loadWeek links this week's own workouts to the open sessions they cover (planned.status='done', workoutId; the workout's plannedSessionId stays null, so the board says "«Walk» counted as HIIT or walk" — DoneItem.standsFor); a second cardio is an extra. Workouts of a one-off session that replaced a program session are left out. Deleting a workout opens its session again (deleteWorkout). Monday's reviewWeek uses the same rule for last week. Program → each session says what counts (counts), and the coach sees it per session.
  • Each week is an instance of the program (lib/training/week-review.ts, week_plans, migration 0036_week_plans): the program is fixed, but on the first visit of a new week loadWeek reviews the last one (reviewWeek) and lays this one out, once (claimWeekReview). A session left undone is not owed when a workout outside the program did its job (covered: any workout for hiit / other / yoga / mobility sessions, the same discipline and half the muscles for strength); otherwise it goes first among this week's sessions of the same discipline (first), or just comes back on its day (kept). Only suggested days move, never the template. Today shows what changed under the week ring (WeekProgress), and the coach reads it in the glance.
  • Monday's review (lib/training/week-adapt.ts › adaptWeek, gathered by lib/services/week-plan.ts, stored as week_plans.review.plan): what a trainer does on Monday, with rules and limits, no AI. It reads last week as trained (program, own workouts, races, effort), gives it a read (solid | mixed | short | heavy | easy | off), sets this week's goal (sessions, cardio minutes, a muscle to watch) and proposes changes to this week only:
    • rest — days off after a big effort (10 km or a hard hour: two days; a half marathon: three), sessions on those days move later;
    • trim — one set fewer on a muscle worked a lot outside the program from Friday on, in the first session that trains it again, plus 15 min of cardio;
    • cardio — up to two 25-min walks on free days when last week had under 30 min of cardio and the program asks for under 60;
    • focus — one more set on a lift with no progress in three sessions (isStalled);
    • ease — one set fewer on the last two exercises of every strength session after a week averaging effort ≥ 8.5. Today shows the note first (components/today/WeekNote.tsx): always an explanation, and when there are changes "Apply" / "Leave the program as it is" (POST /api/week-plan, decideWeekPlan). Accepting writes set counts on this week's sessions (planned_sessions.overrides.sets, applied by applyOverrides) and moves sessions off rest days; until then nothing changes. Afterwards the goal sits under the week ring, free days suggest the walk until the cardio goal is met, and rest days say so. The coach reads the read, the goal and the state of the proposals in the glance.
  • The review is written by AI; the rules are the net (lib/coach/week-review.ts, lib/services/week-ai.ts): one call per person and week on the more capable model (WEEK_REVIEW_MODEL, default the goals model; recorded as feature week_review). gatherDossier gives it the phase goal and where the person is in it, this week's open sessions with their ids, the last four weeks as really trained (own workouts, races, effort, notes), check-ins, weight, lifts that are not moving, food when it adapts, and the rules' plan as a hint. It answers with set_week_plan: the note, this week's goal in one line, and changes from a closed vocabulary (rest, move, skip, light, sets, cardio, each with its reason in the person's language) plus an optional energy change for food. sanitizePlan keeps it inside limits (unknown ids dropped, days within the week, sets within two of the program's, at most two sessions out, three cardio sessions, rest until Thursday, food ±150 kcal) — the model judges, the app applies. The newest models reject a forced tool_choice: the prompt asks for the tool and the answer is read leniently.
    • When: Today asks for it the first time the week's plan is still the rules' (requestWeekReview → netlify/functions/week-review-background.mts; detached in local dev) and the note says "looking at your week" while it lands (aiPendingSince, at most 90 s); the Monday cron asks ahead. A failure marks aiFailed and the rules' plan stands for the week. No key, no budget or weeks that don't adapt: rules only.
    • Mid-week: the coach's revise_week tool re-plans the rest of the week with the same vocabulary and limits ("I've caught the flu"): a new note on Today to accept or decline (reviseWeekFromCoach, prompt › "When the week changes").
    • Food: an accepted energy change is an energy_adjustments row with reason week_review. The rules' weekly food review (runWeeklyReview) steps aside when the week's plan was written by AI or the coach, and on Mondays while the review is due.
  • Who gets it: two switches in Profile → "Weeks that adapt" (users.usage.adaptTraining / adaptFood, on by default, independent of the preset; capabilities().adaptiveTraining / adaptiveFood). Plans decide (PLANS[..].adapt, effectiveAdapt): free none, Entrena training, Coach and Coach+ both; the trial and full access have both. getTodayView(..., { adapt }) hides the note and its suggestions when it is off.
  • Yesterday counts (loadedMuscles, recoveryAdvice, in getTodayView): after a workout done outside the program yesterday, a session that repeats half or more of the muscles worked hard gives way to the pending one that repeats the least (reason: 'recovery'), or to a sport when they all repeat. Easy sessions (effort ≤ 5) ask nothing; the program's own consecutive days and a session the user chose are left alone.
  • One-off sessions (extra_sessions, lib/db/extra-sessions.ts, migration 0035_extra_sessions): a session for one day outside the program ("no HIIT class today, give me a full body"). The coach plans it at once with plan_extra_session (one open per day; planning again replaces it; replacesPlannedId takes a pending program session out of the week). Today shows it first (suggestion.kind === 'extra', view.extra), /log?extra=<id> opens pre-filled and saving closes it as a workout outside the program. "Remove" on the card (DELETE /api/extra-sessions/:id) brings back the session it replaced. The program and its versions are never touched.

Accessibility (a11y) — mandatory patterns

Escape key on every modal

Every modal or overlay must close on Escape. Use this exact pattern:

useEffect(() => {
  if (!open) return                         // only attach when modal is visible
  const onKey = (e: KeyboardEvent) => { if (e.key === 'Escape') onClose() }
  document.addEventListener('keydown', onKey)
  return () => document.removeEventListener('keydown', onKey)
}, [open, onClose])
  • For always-mounted modals (no open toggle), omit the guard: attach on mount, clean up on unmount.
  • onClose must be stable (passed as prop or wrapped in useCallback) to avoid stale closures.

Images

All <img> elements must have user-select: none — enforced globally via app/globals.css.
Never add draggable={true} to images.

Focus rings

All interactive elements (buttons, links, inputs, selects) must have a visible focus ring. Use:

  • focus:outline-none focus:ring-2 focus:ring-black/30 on light backgrounds
  • focus:outline-none focus:ring-2 focus:ring-white/40 on dark backgrounds (e.g. sidebar)

Never use bare focus:outline-none without a replacement ring.

Dropdown / popover pattern

Every dropdown must close on both outside click AND Escape. Use two useEffect calls:

// Outside click
useEffect(() => {
  function handleClick(e: MouseEvent) {
    if (ref.current && !ref.current.contains(e.target as Node)) setOpen(false)
  }
  document.addEventListener('mousedown', handleClick)
  return () => document.removeEventListener('mousedown', handleClick)
}, [])

// Escape key (only attach when open)
useEffect(() => {
  if (!open) return
  const onKey = (e: KeyboardEvent) => { if (e.key === 'Escape') setOpen(false) }
  document.addEventListener('keydown', onKey)
  return () => document.removeEventListener('keydown', onKey)
}, [open])

The trigger button must have aria-expanded={open} and aria-haspopup="true".

Dialogs / modals

Every modal overlay must have role="dialog" and aria-modal="true" on the outermost div, plus an aria-label describing its purpose:

<div role="dialog" aria-modal="true" aria-label="Modal title" className="fixed inset-0 …">

Non-blocking banners (e.g. cookie consent) use aria-modal="false".

Toolbars

Groups of action buttons that operate on a selection (e.g. bulk action bars) must have role="toolbar" and aria-label:

<div role="toolbar" aria-label="Bulk actions" …>

CSS gotchas

Images in cropping/canvas contexts

Tailwind's preflight and browser CSS reset apply max-width: 100% to all <img> elements.
When positioning images absolutely with an explicit pixel width, always add maxWidth: 'none' and maxHeight: 'none' to the inline style, or the image will be clamped to the container width and lose its aspect ratio.

<img style={{ width: dispW, height: dispH, maxWidth: 'none', maxHeight: 'none' }} />

Locked, never hidden (lib/billing/locks.ts, components/billing/{Locked,UpgradeHost,upgrade}.tsx)

  • Anything another plan includes and the person's plan doesn't stays visible and locked: same place and label, fainter, a small lock, aria-disabled="true" (never the disabled attribute), and a tap or Enter opens the one upgrade sheet ("Upgrade your plan to unlock …", the cheapest plan that has it, a button to /plans). Only what the person turned off themself is hidden.
  • computeLocks(ent, billingEnabled(), chosenUsage) is pure and derives everything from PLANS: locked levels per area, locked presets, the two adapt switches, the Food tab, and features (feature → cheapest paid plan). Nothing is locked while payments are off, nor for admins, full access or the trial. It uses the same plan levels the server clamps with, so a lock and a 403 always agree; server gates stay where they are.

To lock a control: <button onClick={…} {...lockProps(lock?.feature)}>Label{lock && <LockMark />}</button> (spread after the control's own onClick); elsewhere call askUpgrade(feature).

Release checklist (production)

Do these in order. Each production step needs the owner's go-ahead.

  1. Dry run against production. Run DATABASE_URL=<prod> npm run db:dry-run and check the row counts and the list of exercise names that had no catalog match.
  2. Apply the migrations. Use the admin banner (/api/admin/run-migrations) or npm run db:apply -- --production. The v2 code reads the new columns and tables, so this must happen before deploying.
  3. Deploy v2 (merge into main).
  4. Cron. netlify/functions/daily-cron.mts is a Netlify Scheduled Function that calls POST /api/cron/daily every hour (idempotent). It needs CRON_SECRET set in Netlify.
  5. Coach streaming timeouts. Coach turns with tools can take 30–120 s. app/api/coach/threads/[id]/messages sets maxDuration = 300, which Vercel honours. Netlify's function limits may be lower, so check the plan's limit, or move the coach endpoint to a background/long-running function.
  6. Smoke test with a real account: build a program with the coach, log a session, swap an exercise, check Progress.

Deferred migration — drop v1 tables

Only after v2 has run in production for a while and the data has been checked. Add it as 0035_drop_legacy (the next free id) in lib/db/migrations.ts, with destructive: true (deploys never apply destructive migrations on their own; the owner applies it by hand). Its check is "table routines does not exist". Then remove the v1 tables from lib/db/schema.ts and from app/api/admin/db-check/route.ts, and remove migration 0017, which reads them.

DROP TABLE IF EXISTS images, image_folders, pinterest_boards, pinterest_pins;
DROP TABLE IF EXISTS routines, routine_sessions, exercises, workout_logs, ai_conversations, training_types;

Ads (only on the free plan)

Ads stay off in production (ADS_ENABLED unset). Serving them in the EU needs a Google-certified CMP (IAB TCF 2.2) with Consent Mode v2; the current CookieBanner is not certified. Before turning ADS_ENABLED=true: add a certified CMP, wire Consent Mode v2, and update the cookie policy. Paid plans and the trial never show ads (lib/billing/entitlements.ts).

Performance: future improvements (study of 2026-10-19)

Measured on a phone emulation (4× slower CPU, 150 ms RTT, 1.6 Mbps): the landing shows content at 2.4–2.9 s, register and login at 2.1–2.3 s, with no layout shift. Fonts, GA and zod in the browser were fixed the same day. Each of these needs its own validation before it ships:

  • Landing from Netlify's CDN. / renders on every visit (~0.5 s before the first byte) because it reads the language cookie, Accept-Language and the session. Move the signed-in redirect to proxy.ts, render one landing per language, and cache it at the edge (CDN-Cache-Control + Netlify-Vary: cookie=lang, header=Accept-Language): ~50 ms instead of ~500 ms. Validate the redirect of signed-in people and the language picked.
  • Translations per language. Login, register and every app screen download the three languages (lib/i18n/translations.ts, ~68 KB gzipped); one would be ~23 KB. It needs one file per language and I18nProvider loading only the person's (the dictionaries hold functions, so they can't go through the RSC payload).
  • Today's repeated reads. Today reads some tables two or three times per load (planned sessions, workouts, check-ins, the meal week) through different services. Fast today (~25 small queries, ~30 ms locally); share the reads when it grows.
  • Duplicate prefetches on the landing. /register and /legal/cookies are prefetched twice each (two router-state hashes).
  • Know where visitors come from. Without Google Analytics there is no landing → sign-up funnel nor traffic source. Options: a real GA4 id in NEXT_PUBLIC_GA_ID (Consent Mode is in place; the example id G-XXXXXXXXXX loads nothing), or a cookieless count of landing visits by utm_source in product_events.

Widgets for Today (ideas, not planned yet)

Decided 2026-10-06: the week calendar is off Today, and it lives only in /calendar. Today stays focused on what's due now. When we don't know how to improve the product next, pick from this list. Validate each with beta data first, e.g. which screens people open and what they ask the coach.

Calendar, other ways to show it

  • A collapsed "this week" row: tap to expand to the week as a to-do list. Hidden by default.
  • A streak or consistency heatmap, like GitHub or Strava: a small grid of the last 8–12 weeks.
  • Next session countdown ("Lower A, tomorrow"), with a link to Calendar.

Training

  • Readiness or recovery score, like WHOOP: from sleep, RPE and soreness. Needs a wearable or a daily question.
  • Phase progress ("week 3 of 8 · recomposition") as a slim progress bar.
  • A PR highlight of the week ("New best: bench 105 kg").
  • Volume per muscle as a body map, like Hevy, with this week vs the average.
  • A soreness body map from the daily check-in.

Food and body

  • Macro rings for the day, like MyFitnessPal: Precise level only.
  • A weight trend sparkline with the phase band, like MacroFactor.
  • Water intake, tapped in glasses.
  • A habit checklist: supplements (creatine, vitamin D), steps, sleep hours.
  • A shopping and batch-cooking reminder on the chosen day.

Coach

  • A daily insight card: one sentence from the coach, generated once a day by the cheap model, cached.
  • A "this week's plan changed" summary after the adaptive review. This exists as a note; it could become a widget.

Integrations and platform

  • Steps, sleep and heart rate from Apple Health / Google Fit (needs a native wrapper).
  • Weather for outdoor runs.
  • Home-screen and lock-screen widgets on iOS/Android (native app only).

Customisation

  • Let people choose and reorder Today's widgets, within the usage profile's limits, with sensible defaults per profile.

Production migrations on deploy — done

Built (see ai/AGENTS.md → Migrations):

  • Apply on deploy: ✅ Netlify runs npm test && npm run migrate:deploy && npm run build. In the production context only, scripts/migrate-on-deploy.mts dry-runs every pending migration (one transaction, rolled back) and then applies them, only when all are additive. A pending destructive: true migration fails the build until the owner applies it by hand.
  • Guard: ✅ reading users survives a pending migration that adds columns (selectUsers in lib/db/users.ts falls back to the columns that exist), so the app and the admin banner still load.
  • CI: ✅ .github/workflows/ci.yml runs the tests (Netlify-like env, including COACH_MONTHLY_TOKEN_LIMIT=0) and types on every push and PR to main. Lint runs there too but doesn't block yet: older auth and banner screens still have lint errors to clear.
  • Still the rule — expand/contract: a release only adds (columns, tables, indexes) and its code works with or without them; removals go in a later release, flagged destructive.

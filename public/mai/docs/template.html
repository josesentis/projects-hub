TEMPLATE.md — Guia de sincronització template ↔ app

Aquest document explica la relació entre el template i l'app que n'ha derivat, i defineix el procés per sincronitzar millores genèriques de l'app cap al template.

Contexte

El template (app-template) és un esquelet genèric per construir web apps amb Next.js, Supabase, autenticació completa, i un sistema de referències (imatges + Pinterest). Conté tot el que és reutilitzable entre apps però res que sigui específic d'un producte concret.

L'app real ha evolucionat des d'aquest template, afegint funcionalitats pròpies del producte. Cada cert temps, convé identificar quines d'aquestes millores son prou genèriques per tornar al template.

Anatomia del template: el que hi ha

Infraestructura

  • Auth completa — email/password, OAuth (Google + Apple), verificació d'email, reset de password, sessions JWT amb renovació sliding-window
  • Base de dades — Drizzle ORM + PostgreSQL (Supabase). Schema: users, images, imageFolders, pinterestBoards, pinterestPins, leads, usageTokens, usageEvents, pushSubscriptions
  • Emmagatzematge — Supabase Storage (bucket uploads)
  • Email — Resend per emails transaccionals (verificació, reset de password)
  • Deploy — Netlify + @netlify/plugin-nextjs

Dashboard shell

  • Sidebar col·lapsable (desktop) amb navegació i settings
  • TopBar per a mòbil
  • MobileNav — navegació inferior per a mòbil
  • SettingsPanel — tauler lateral de configuració

Sistema de References

La funcionalitat core del template és la gestió de referències visuals:

  • Upload d'imatges — seleccionador de fitxers, camera (mòbil)
  • Import de Pinterest — scraping de boards públics → crea carpeta + importa imatges
  • Organització — carpetes, drag & drop per reordenar, moure entre carpetes
  • Favorites — toggle per marcar imatges favorites
  • AI Analysis — analitza imatges amb Claude (POST /api/analyze/[id])
  • Visualització — masonry grid, modal de detall

Regla per decidir si algo va al template

Fes-te aquestes preguntes:

"Funcionaria exactament igual en una app completament diferent (e.g. una app de receptes, una app de gestió de tasques, una app de portfolio)?"

Sí → va al template No → queda a l'app
Sistema de carpetes d'imatges Funcionalitat específica del producte
Nou mètode d'autenticació Lògica de negoci de l'app
Millora de la UI del sidebar Pàgines específiques de l'app
Nou camp genèric al perfil d'usuari Taules de DB específiques del producte
Millora al sistema de notificacions push Integracions externes específiques
Nou component UI genèric (toast, modal...) Components que depenen de dades del producte
Millora de rendiment / accessibilitat
Nova secció de landing page genèrica
Millora al sistema d'anàlisi d'imatges

Procés de sincronització app → template

Quan l'app ha implementat alguna cosa que sembla prou genèrica per al template, segueix aquest procés:

Pas 1: Identificar el que cal sincronitzar

A l'app, demana a Claude:

Revisa els canvis des de [data/commit] i diga'm quines implementacions son prou 
genèriques per actualitzar el template. Classifica-les com:
- TEMPLATE: va al template sense modificació
- TEMPLATE-ADAPT: va al template però adaptant-lo per fer-lo genèric
- APP-ONLY: específic d'aquesta app, no va al template

Pas 2: Documentar cada millora

Per cada cosa a sincronitzar, prepara una fitxa:

## [Nom de la funcionalitat]

**Tipus:** TEMPLATE / TEMPLATE-ADAPT
**Fitxers afectats a l'app:** 
- `path/al/fitxer.ts` (descripció del canvi)

**Descripció:**
Explica QUÈ fa i PER QUÈ és genèric.

**Canvis necessaris per adaptar al template:**
(Si cal treure referències específiques de l'app, adaptar noms, etc.)

**Dependències noves:** (packages, env vars, etc.)

Pas 3: Venir al template

Obre una sessió al projecte app-template i explica:

Vull sincronitzar les seguents funcionalitats de l'app cap al template:

[Pega les fitxes del pas 2]

Implementa-les seguint el mateix estil i convencions del template.

Claude del template tindrà en compte:

  • Les convencions de codi del template (sense comentaris innecessaris, sense mocks)
  • Que els tests siguin obligatoris per cada canvi
  • La compatibilitat amb les 3 llengues d'i18n
  • L'accessibilitat (escape key, focus rings, aria labels)

Pertany al TEMPLATE (genèric)

  • Dashboard shell + navegació

  • Settings
  • Admin (users, analytics, impersonació, run-migrations)
  • Landing shell (Nav, Pricing, Footer, Manifesto, seccions genèriques)
  • i18n (en/es/ca)
  • Notificacions push
  • Cron diari
  • Waitlist / leads
  • AdSense + AdBlock
  • PWA (install banner, update banner)

Notes tècniques per al Claude del template

Quan implementis alguna cosa al template, tingues en compte:

  1. Tests obligatoris — cada nou fitxer a lib/ necessita test a tests/lib/. Cada nova ruta protegida necessita test a tests/proxy.test.ts
  2. i18n complet — cada string visible a l'usuari ha d'estar a les 3 llengues del fitxer lib/i18n/translations.ts
  3. Accessibilitat — escape key als modals, focus rings, aria labels (segueix les regles d'ai/AGENTS.md)
  4. No AI sense ANTHROPIC_API_KEY — les funcions d'IA han de fallar graciosament si no hi ha clau configurada
  5. Schema DB — qualsevol canvi al schema necessita actualitzar app/api/admin/run-migrations/route.ts amb la migració corresponent
  6. Proxy — noves rutes protegides han d'afegir-se a AUTH_REQUIRED a proxy.ts
  7. Variables d'entorn — noves env vars han de documentar-se a SETUP.md
